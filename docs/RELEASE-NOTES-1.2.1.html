Release Notes — v1.2.1

Spam Protection & Security Hardening

Highlights

Version 1.2.1 replaces the contact form's captcha with a built-in, invisible spam protection — no configuration, no external services, no puzzle for your visitors. It works out of the box and is GDPR-friendly: no visitor data is sent to third parties and no cookie consent is required.

It also ships a broad security-hardening pass for the admin backend: every action that changes your site now requires a valid admin session and a CSRF token, all public output is escaped against cross-site scripting, and several older weaknesses in the password reset, file uploads and the extension marketplace have been closed.

  • Invisible honeypot field that traps form-filling bots
  • Signed form tokens — bots posting directly to the form handler are blocked entirely
  • Time trap — submissions faster than a human could type are rejected
  • Rate limiting — at most 3 messages per 10 minutes per visitor
  • Strict server-side validation of every submission
  • Google reCAPTCHA has been removed
  • All admin actions now require login + CSRF protection
  • Cross-site scripting (XSS) output escaping across the public site and backend
  • Hardened password reset, image uploads and marketplace downloads

New: Invisible Spam Protection

Previously, the contact form's only defense was an optional Google reCAPTCHA — and its server-side check was broken, so bots could flood your inbox by posting directly to the form handler. v1.2.1 closes this completely with four layers that are invisible to real visitors:

  • Signed form token: every contact form embeds a cryptographically signed token bound to the form and the time it was rendered. Requests without a valid token — i.e. every bot that posts directly to the handler — are dropped without sending a mail.
  • Honeypot: an invisible extra field that humans never see. If it is filled in, the sender was a bot and the message is discarded.
  • Time trap: submissions arriving less than 3 seconds after the page was rendered are treated as bots. Forms older than 24 hours ask the visitor to reload the page.
  • Rate limiting: a maximum of 3 messages per 10 minutes per visitor — even a bot with a valid browser session can no longer flood your inbox.

Blocked bots are shown a normal "message sent" page so they don't learn how to adapt; real visitors who hit the rate limit or a validation error see a clear message explaining what to do.

GDPR / Privacy

  • No external services: the Google reCAPTCHA integration (including its script embed) has been removed. Your one-pager no longer loads anything from Google for the contact form, so no consent banner is needed for it.
  • No plain-text IP storage: the rate limiter never stores visitor IP addresses. It only keeps a keyed hash (HMAC with a secret generated on your own server), and entries are deleted automatically after one hour.

Security Hardening

This release fixes a class of issues where admin-only actions could be triggered by visitors who were not logged in, and where content could be manipulated through the browser of a logged-in administrator. If your site is publicly reachable, updating is strongly recommended.

  • Login required for every change: all backend action handlers (saving sections, design, settings, account changes, uploads, extension management, …) now verify an admin session. Previously many of them accepted requests from anyone.
  • CSRF protection: every admin form now carries a one-time security token that is checked on submit, so a malicious website can no longer make your browser perform backend actions while you are logged in. Blocked requests show a "Security check failed" page asking you to reload and retry.
  • Password reset fixed: the new password is now always e-mailed to the address stored for the account, never to an address supplied in the request. The endpoint no longer reveals whether a username or e-mail exists and is rate-limited.
  • No more arbitrary file deletion: removing a section's background image is now restricted to the image upload folders. Crafted requests can no longer delete files outside them (for example the database file).
  • Cross-site scripting (XSS) escaping: titles, the site title, the meta description, navigation entries, background paths and similar values are now HTML-escaped wherever they are printed, on both the public site and the backend editors. Your rich-text section content keeps rendering as HTML as before.
  • Hardened image uploads: uploads are now content-checked as real images (fail-closed), the file size limit is actually enforced, and the upload folders ship with an .htaccess that forbids executing scripts placed there.
  • Safer marketplace & updates: extension and theme downloads are now forced over HTTPS and blocked from reaching internal/private network addresses (SSRF protection).
  • More hardening: the login now regenerates the session ID and throttles repeated failed attempts per IP; internal Referer-based redirects are validated to the same site; database errors are written to the server log instead of being shown to visitors; user names and host names are escaped in notification e-mails.

Contact Form Fixes

  • Mail header injection fixed: the contact form's Reply-To header is now built only from a validated e-mail address; line breaks are stripped. (This also fixes a bug where Reply-To was never set at all — replying to contact messages now works.)
  • Unauthenticated settings endpoint removed: misc/changecaptcha.php accepted requests without an admin session. The file has been deleted along with the reCAPTCHA feature.
  • Strict server-side validation: the handler now validates required fields, e-mail format and input lengths, and the notification mail contains only the actual form fields (Name, Mail, Message) instead of the raw request data.
  • The success and error pages for the contact form now always show a proper headline and message (previously they could be blank).

For Theme Developers

If your theme overrides the section-contact template, it must render the new protection fields inside the form — otherwise submissions will be silently dropped by the handler. It is two lines of code; see the "Contact form spam protection" section in docs/EXTENSIONS.md and the reference implementation in themes/agency/templates/section-contact.php. Themes using the documented class_exists() guard remain compatible with older CMS versions.

Escape your output. Custom themes are responsible for escaping the values they print. The CMS can only escape inside its own bundled templates — it cannot reach into yours. Wrap any user-controlled value (section title, muted title, background path, site title, navigation entries, footer links, additional-page title, …) with the new helper opcms_esc() when you print it in HTML or attribute context, e.g. <?php echo opcms_esc($section->getTitle()) ?>. Leave intentionally rich content (a section's rich-text body, the Extra CSS and Google Analytics settings) raw, exactly as the bundled agency theme does. See themes/agency/templates/ for the updated reference.

How to update — v1.2.1

No manual database migration is required. The new spam protection and the security fixes work as soon as the new files are in place. Running update.php once (step 4 below) simply adds the new "Security check failed" status message text; without it, blocked requests are still stopped, they just show a generic page.

  1. Save your database — copy database/SQLiteDatabase.db to your computer.
  2. Download v1.2.1 from onepagercms.de.
  3. Upload the new files to your webspace and override all existing files. This adds the new system/ helpers, the misc/inc/auth.php guard and the .htaccess files in the img/ upload folders. Then delete misc/changecaptcha.php from your webspace if it is still there.
  4. Restore your database — upload the SQLiteDatabase.db you saved in step 1 back into the database/ folder. Then open https://your-domain.tld/update.php once in your browser to add the new status message, and delete update.php from your webspace afterwards. This step is safe to run repeatedly and never touches your content.

Updating from v1.1.0 or older? The same update.php run in step 4 also applies all missing migrations up to the current version — exactly as described in the v1.2.0 release notes.

After updating:
Because the login now issues a fresh session on sign-in, you may be asked to log in again once. If you use a custom theme, remember that its templates need their own XSS escaping (see "For Theme Developers" above) — the CMS only escapes inside its bundled themes.
Note on the Captcha setting:
The reCAPTCHA option has been removed from the settings page and from the Contact section editor. Existing contact sections keep working unchanged — the captcha checkbox and API key are simply ignored. You can delete your reCAPTCHA API key in your Google account; the CMS no longer uses it.
